# JavaScript and TypeScript files (*.js, *.ts)

- __Consistency__: Follow the existing codebase's conventions unless explicitly instructed otherwise. Avoid unrelated refactoring or stylistic changes when implementing a requested feature or fix.
- __Semicolons__: Use semicolons at the end of statements where appropriate. Do not add semicolons after block statements, such as function declarations, class declarations, and control structures.
- __Exports__: Prefer one default export per module when appropriate. Use named exports when they better suit the module's purpose or existing conventions.
- __File naming__: Use consistent, descriptive file and folder names. Prefer naming conventions that group related files together in directory listings.
- __File extensions__: Prefer .js and .ts for JavaScript and TypeScript code. Avoid .vue files; use standalone JavaScript or TypeScript modules instead, unless explicitly instructed otherwise or required by the project.
- __Variable declarations__: Prefer const for variables that are not reassigned. Use let when reassignment is necessary, and avoid var in modern JavaScript and TypeScript.
- __Function declarations__: Function declarations, function expressions, and arrow functions are all acceptable. Choose the appropriate form based on context and existing conventions.
- __Modularity and portability__: Prefer self-contained, loosely coupled folders that can be lifted into a new project with minimal chanes and minimal collision risk. Keep dependencies explicit and minimize dependencies on code outside the folder. Prefer relative imports for dependencies within the same folder or module. Expose a clear public interface for functionality used by other modules when appropriate. Treat this as a design preference, not a strict requirement; prioritize simplicity and consistency with the existing project.
- __Error handling__: The global rules from `04-code-style-errors.md` still apply to JavaScript and TypeScript: fail early, prefer explicit error messages, do not over-validate. On top of that, all executed code must be wrapped with a project-specific error-handling proxy function. The exact mechanism varies by project — it may be a global function such as `window.logError` (or something similar in the global namespace), a module every child component must import to report errors, a global error handler defined in app setup and passed to components via props, or a handler passed to components through a unified store. Regardless of mechanism, some error wrapper must always exist, and code must always execute within it.
  - __Synchronous code__: call the error wrapper once at the root level. If a module implements functionality, does not know who calls it, could have its error intercepted, and has access to the project-specific error wrapper, it should still use that wrapper — reporting an error twice is safer than missing it.
  - __Setup code__: synchronous code executed from app or component setup is the same, except the error wrapper cannot be relied upon because the app or component may fail to render entirely. The logic is unchanged: still attempt to use the error wrapper where possible.
  - __Asynchronous code__: do not rely on root-level interception. Wrap the executed code with the error wrapper again whenever it runs asynchronously — event handlers, click events, timeouts, `Promise.then()`, and similar. This is unnecessary when the async code is called with `await` and the error will be intercepted at the root level.
- __Promises (`Promise.then` vs `async`/`await`)__: Prefer `async`/`await` when there is no reason to use `Promise.then` and the code can be expressed that way — it is usually cleaner and more readable. `Promise.then` is legitimate when the code is not a simple sequence but implies tasks that do not necessarily finish before the next task should start. Either way, ensure all error handling is done properly: the final message for any failure in any async code is always delivered to the user through the global error wrapper (see the error-handling point above). A rejected promise interrupts execution and behaves like an exception, but it is not necessarily an error — for example, a modal where the user must select a file and clicks "cancel" should call `Promise.reject`, be intercepted, but not be shown as an error. A real error, however, must be shown and intercepted. When there is no better way to distinguish a cancel event from an error, use `e instanceof Error`.
